# 문제 정의 (펭귄 실습 프로세스)

모호하고 막막한 문제를, 바로 손댈 수 있는 한 줄짜리 문제 정의로 바꾸는 6단계 절차.
각 단계는 상류 개념(무엇을 하는 단계인가)으로 정의되고, 예시는 그 개념이 한 사례에서 나타난 모습이다. 예시의 틀(input/output 등)을 다른 문제에 그대로 강요하지 않는다.

## 언제 쓰나
- 사용자가 프롬프트로 고민이나 문제를 이야기하면서 "막막하다", "어디서부터 하지", "한 번에 안 떠오른다" 같은 상태를 드러낼 때
- 사용자가 /problem-definition, "문제 정의 해줘", "문제 정의 실습"을 요청할 때

## 진행 원칙
- 2단계(짚기)와 3단계(구체화)의 답은 사용자의 지식·감각에 달려 있다. Claude는 후보를 제시하고 사용자 확인을 받는다. 사용자가 "알아서 해"라고 하면 가장 그럴듯한 후보로 진행하고, 그렇게 골랐다고 한 줄로 밝힌다.
- 각 단계 결과는 한 줄로 짧게 적고, 손메모처럼 화살표로 이어지는 흐름을 유지한다.
- 앞 단계로 돌아가는 건 실패가 아니라 정상 동작이다.

## 절차

### 1. P_ 날것 그대로 적기
느끼는 그대로의 한두 문장. 감정·막막함 표현을 지우지 않는다. 거기에 단서가 있다.
- 사용자가 프롬프트로 고민·문제를 이미 이야기했으면, 그 말이 곧 P_다. Claude는 새로 쓰게 하지 않고 사용자 표현을 그대로 옮겨 P_로 제시한다.
- 길면 핵심 한두 문장만 추리되, 사용자가 쓴 단어(특히 감정·비유 표현)는 바꾸거나 다듬지 않는다. 다듬는 순간 2단계에서 짚을 단서가 사라진다.
- 문제가 아직 말해지지 않았을 때만 "지금 느끼는 그대로 한두 문장으로 적어 주세요"라고 요청한다.
예: P_ 제품과 달라서 청구항을 꽤 크게 고쳐야 하는데, 한번에 탁 하고 떠오를 것 같지 않음.

### 2. 모호한 단어 짚기 (탐지)
문장 속 모호한 표현을 모두 찾은 뒤 하나만 고른다. 선택 기준:
- 이 단어가 구체화되면 문장 전체의 막막함이 풀리는가? (가장 중요)
- 비유적이라 내용이 비어 있는가?
- 숨은 전제를 품고 있는가? (예: "답은 한 번의 통찰로 와야 한다")
예: "한번에 탁"

### 3. "그게 어떤 것인데?" — 구체화 (해소)
고른 단어를 그대로 받아 묻는다. 답은 관찰·조작 가능한 대상이어야 한다. 느낌이나 방식이 대상으로 바뀌면 성공.
예: 그게 어떤 것인데? → 제품의 동작과 원리

### 4. 필요 요소 도출 — "됐다 가정하고, 그걸 위해 무엇이 필요한가?"
3단계의 답이 이미 달성됐다고 가정하고, 그것을 위해 무엇이 필요한지 거꾸로 도출한다. 도출한 필요 요소는 문제에 맞는 분류 틀로 나눠 적는다.
- 분류 틀은 문제마다 고른다. 장치·기능이면 input/output, 현상이면 원인/결과, 일·프로젝트면 정보/자원/허락, 관계면 나/상대/상황 등.
- 기준: 이 요소들이 다 확보되면 3단계의 답이 성립하는가?
예: 제품의 동작과 원리를 안다고 가정 → 그걸 위해 필요한 것 = input과 output

### 5. 필요 가치 판별 — "A가 아니라 B여야 한다"
4단계의 필요 요소가 무엇에 봉사해야 하는지, 즉 그 요소들이 내야 할 가치·기능을 가른다. 그럴듯하지만 틀린 후보 A와 실제로 필요한 B를 나란히 적고, 각각의 기능을 옆에 단다. B를 고른 근거(현실·대상과 맞는 쪽)를 한 줄 남긴다.
- A는 보통 기존 관성·익숙한 해석·처음 떠오른 목적이다. A를 명시해야 B가 또렷해진다.
예: 둘(input·output)의 필요 가치가 서멀 사이클 상황(→ 반응 용기의 온도 관리)이 아니라 히트리드(→ 응결 방지)여야 한다.

### 6. 목적 지향 재진술 — "즉, ~"
5단계의 가치(B)와 4단계의 필요 요소를 결합해, 문제를 한 줄짜리 탐색 과제로 확정한다.
형식: 즉, [B의 기능]을 위한 [4단계 필요 요소] 찾기
예: 즉, 응결 방지를 위한 input·output 찾기

## 마무리 점검 (짧게, 각 한 줄)
정의를 확정하기 전에 세 질문에 답한다. 하나라도 막히면 표시된 단계로 돌아간다.
1. 완성 판정: 답 후보를 들고 왔을 때 맞는지 기계적으로 판정할 기준을 적을 수 있나? (예: 청구항 각 구성 ↔ 제품 부품·동작 대응표가 모두 채워짐) → 막히면 6단계 보강
2. 제3종 오류: 이 정의를 완벽히 풀면 원래 목적이 달성되나? → 아니면 5단계로 돌아가 대안 B'를 하나 더 세워 비교
3. 높이: "무엇이 막고 있나?"를 한 번 묻고, 더 아래 칸에 진짜 장애물이 있으면 정의를 그 높이로 내린다. (예: 히트리드 자체는 공지 기술 → "이 제품만의 응결 방지 방식"으로)

## 출력 형식
```
P_ (날것 문장 — 사용자 표현 그대로)
 └ 짚은 단어: …
   └ 그게 어떤 것인데? → (구체적 대상)
     → 됐다 가정, 필요한 것: (필요 요소, 분류 틀)
       → A(기능)가 아니라 B(기능)
         ⇒ 즉, [B의 기능]을 위한 [필요 요소] 찾기
점검: 판정 기준 … / 3종 오류 … / 높이 …
```

## 배경 (참고용, 답변에 늘어놓지 않는다)
- 2단계: 모호성 탐지, 가정 드러내기
- 3단계: 명료화 질문(클린 랭귀지형 "그 X는 어떤 X인가"), 조작적 정의
- 4단계: 목표 상태에서 거꾸로 필요 조건 도출(Pólya의 working backwards)
- 5단계: 어떤 가치를 고르느냐가 해법의 방향을 정한다(Rittel & Webber)
- 점검: Simon의 잘 구조화된 문제 조건, Mitroff의 제3종 오류, Basadur의 질문 사다리
