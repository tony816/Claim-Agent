# 08. 종속항 기술기여 게이트

> **용도:** 종속항 후보가 도면상 형상이나 실시형태를 단순 묘사하는 데 그치지 않고, 현재 발명의 원자료가 뒷받침하는 기술적 과제·추가 기술특징·작동 또는 협동 원리·효과의 인과사슬을 가지는지 검증한다. 검증된 후보만 종속항 트리 설계의 주된 권리화 축으로 잠근다.
>
> **역할 제한:** 이 문서는 현재 발명의 기술내용, 효과, 수치, 재료 또는 선행기술을 제공하는 원자료가 아니다. 원자료에 없는 과제·작용·효과를 만들어 후보를 통과시키지 않는다.
>
> **활성 시점:** 변경 없는 루트 독립항에 유효한 `DRAFT_CLAIM_LOCK` 또는 `FINAL_CLAIM_LOCK`이 생긴 뒤, `claim-drafter`가 `draft_scope: DEPENDENT_SET` PRE_STYLE 의미 초안을 작성하기 전에 활성화한다. `05_종속항_전개패턴_가이드.md`보다 먼저 기술기여 후보를 선별하고, 그 결과를 입력으로 종속항 트리를 설계한다. 최종 표면 문언은 drafter 뒤 별도 `claim-style-adjuster`가 확정한다.

---

## 1. 기본 원칙

### 1.1 효과 문구가 아니라 효과를 발생시키는 기술특징을 한정한다

청구항에는 `성능이 향상되는`, `안정성이 우수한`과 같은 설명·평가 문구를 장식적으로 삽입하지 않는다. 현재 원자료가 뒷받침하는 구조, 배치, 결합, 재료, 수치, 처리 단계, 상태전이 또는 제어조건 중에서 기술적 과제를 해결하는 작동·협동 원리를 실제로 형성하는 특징을 한정한다.

효과가 기능적 한정의 일부로 필요하다면 다음을 모두 만족해야 한다.

- 효과 또는 결과가 객관적으로 판별 가능한 기술 상태일 것
- 그 상태를 만드는 수단·관계·조건이 청구항에서 닫힐 것
- 현재 원자료에 해당 인과관계의 근거가 있을 것
- 결과만 기재하여 임의의 미공개 수단까지 포섭하지 않을 것

### 1.2 종속항의 기술적 가치는 인용항을 포함한 전체 조합에서 본다

부가한정 하나만 떼어 독립적인 발명이라고 가정하지 않는다. 부모항 체인에 누적되는 구성과 부가한정이 함께 어떤 과제를 해결하고 어떤 작용효과를 만드는지 평가한다. 다만 단순한 부품 추가, 통상 재질, 임의 치수 또는 도면 윤곽이 전체 조합에서도 새로운 작동관계를 만들지 못하면 전략 종속항의 우선 후보로 삼지 않는다.

### 1.3 선행기술 없이는 진보성을 PASS로 판정하지 않는다

현재 원자료만으로는 `기술기여 후보`와 `과제해결 관련성`을 판정할 수 있다. 신규성·진보성은 실제 선행기술 집합이 제공된 경우에만 문헌별 개시, 차이점, 결합동기, 변경 용이성, 변경 저해 및 효과의 예측 가능성을 비교한다. 선행기술이 없으면 `INVENTIVE_STEP: UNVERIFIED — PRIOR_ART_NOT_PROVIDED`로 두며, 이 비게이팅 상태만으로 잠정 종속항 설계를 막지 않는다.

### 1.4 형상도 기술적 인과관계가 있으면 후보가 될 수 있다

형상이라는 이유만으로 배제하지 않는다. 형상이 하중 전달, 유동, 정렬, 구속, 차폐, 열전달, 광경로, 접촉, 변형, 진동 또는 제어 입력과 같은 작동원리에 인과적으로 관여하고 그 관계가 원자료로 뒷받침되면 기술기여 후보가 될 수 있다. 반대로 도면에 보인다는 이유만으로 윤곽·각도·위치를 나열하고 작동상 이유를 확인할 수 없으면 `DRAWING_ONLY`다.

## 2. 입력 하드 게이트

다음 입력이 모두 있어야 한다.

- `request_mode: AUTHORING_DRAFT | FINALIZATION`
- `AUTHORING_DRAFT`이면 유효한 `DRAFT_CLAIM_LOCK` 또는 `FINAL_CLAIM_LOCK`, `FINALIZATION`이면 유효한 `FINAL_CLAIM_LOCK` 전문
- 루트 `candidate_id`, `revision`, `design_revision`과 변경 없는 독립항 전문
- `dependent_set_id`와 목표 `dependent_design_revision: ddN`
- USER_LOCK 원문 또는 `없음`
- 현재 발명의 원자료의 정확한 경로 또는 요청 본문에 제공된 원문
- 선행기술의 정확한 경로 또는 `PRIOR_ART_SET: NONE`

LOCK의 문언·식별자·USER_LOCK·근거 원자료·선행기술 집합 중 하나라도 현재 입력과 다르면 기존 종속항 설계와 문언을 무효화하고 `BLOCK — ROOT_LOCK_MISSING_OR_STALE`로 반환한다.

## 3. 후보별 필수 인과기록

각 후보에는 안정적인 `DC-NN` 식별자를 부여하고 다음 필드를 모두 기록한다.

| 필드 | 필수 내용 |
|---|---|
| 후보 ID | `DC-01`, `DC-02` 등 안정적인 식별자 |
| 원자료 근거 | 파일·페이지·문단·도면부호 또는 사용자 원문의 정확한 위치 |
| 부모항 전체 조합 | 후보가 의존하는 루트 구성과 선행 종속 한정 |
| 해결하려는 기술적 과제 | 원자료에 명시되거나 원자료의 기술관계에서 직접 도출되는 구체적 과제 |
| 추가 기술특징 | 구조·관계·조건·단계·재료·수치의 최소 단위 |
| 작동·협동 원리 | 추가 특징이 부모항 구성과 어떻게 상호작용하는지 |
| 발생 효과 | 위 원리로 인해 생기는 객관적인 기술 결과 |
| 인과사슬 | `과제 → 추가 특징 → 작동·협동 원리 → 효과`의 누락 없는 설명 |
| 청구 가능 표현 | 효과 설명을 기술수단·관계·조건으로 변환한 의미 한정 패키지 |
| 형상·공간 객체 계약 | 해당하는 경우 `실제 물체·면 / 관찰 단면·기준 / 단면에 나타나는 외곽선·윤곽 / 형상 술어의 귀속 주체 / 방향·개방 대상 / 원자료 근거`; 해당 없으면 `해당 없음` |
| 선행기술 대비 | 문헌별 개시·차이·결합동기·예측 가능성 또는 `UNVERIFIED` |
| 회피설계·보정 가치 | 우회 난이도, 탐지 가능성 및 예비 보정축으로서의 이유 |
| 분류 | 제4절의 정확한 상태 |

원자료가 효과를 명시하지 않더라도 통상의 기술자가 원자료에 기재된 구조·작동관계에서 직접 확인할 수 있는 결과라면 `명확히 도출`로 사용할 수 있다. 이 경우 명시 근거와 도출 논리를 분리해 기록한다. 도면만 보고 새로운 작동원리나 효과를 창작하지 않는다.

## 4. 후보 분류

### `TECHNICAL_SOLUTION_CANDIDATE`

다음을 모두 만족한다.

- 추가 기술특징과 인과사슬에 현재 원자료 근거가 있음
- 부모항 전체 조합에서 구체적인 기술적 과제를 해결함
- 효과 문구가 아니라 효과를 만드는 수단·관계·조건으로 청구 가능함
- 단순 외관 묘사나 서로 무관한 구성의 집합이 아님

선행기술이 없을 때도 이 분류는 가능하지만, 진보성은 별도로 `UNVERIFIED`다.

### `FALLBACK_ONLY`

원자료 근거와 청구 가능성은 있으나 새로운 과제해결 인과관계가 확인되지 않은 후보다. 명확한 보정·실시형태 포섭·침해 입증 가치가 있을 때만 보조 후보로 유지한다. 선행기술 미제공에 따른 진보성 `UNVERIFIED`만으로 `TECHNICAL_SOLUTION_CANDIDATE`를 이 분류로 낮추지 않는다. 사용자가 기술기여 종속항만을 요청한 경우 주된 종속항 세트에 넣지 않는다.

### `DRAWING_ONLY`

도면의 윤곽, 개수, 방향, 위치 또는 상대 치수를 묘사하지만 그 특징이 해결하는 과제, 부모항과의 작동·협동 원리 또는 효과의 원자료 근거를 확인할 수 없는 후보다. 주된 종속항 트리에서 제외한다.

### `UNVERIFIED`

기술적 가능성은 있으나 과제, 인과관계, 효과, 원자료 위치 또는 필요한 선행기술이 부족한 후보다. 추정으로 승격하지 않고 필요한 자료를 특정한다.

### `RETURN_TO_ARCHITECT`

후보를 제대로 청구하려면 루트 독립항의 주골격, 최소충분 한정, 구성 계층, 기술 개념 또는 SOURCE_EXACT_TERM을 바꾸어야 하는 경우다. 종속항으로 강행하지 않고 새 `design_revision`으로 `claim-architect`에 되돌린다.

## 5. 필수 게이트

### 5.1 `DEPENDENT_SOURCE_GATE`

- `PASS`: 추가 특징, 과제, 작동관계 및 효과의 근거 위치가 모두 확인됨
- `REVIEW`: 명시 근거와 명확한 도출 범위에 사용자 판단이 필요함
- `BLOCK`: 원자료에 없는 내용을 만들어야만 후보가 성립함

### 5.2 `CAUSAL_CONTRIBUTION_GATE`

- `PASS`: 부모항 전체 조합에서 과제–특징–원리–효과가 닫힘
- `REVIEW`: 복수의 인과모델이 가능하거나 효과 귀속이 불명확함
- `BLOCK`: 단순 형상 묘사·부품 나열·통상 선택에 그침

### 5.3 `CLAIMABILITY_GATE`

- `PASS`: 효과를 만드는 기술수단·관계·조건으로 의미 한정 패키지를 작성할 수 있음
- `REVIEW`: 기능적 결과와 구체 수단 사이의 적정 범위 선택이 필요함
- `BLOCK`: 효과 또는 목적 문구만으로만 표현할 수 있거나 카테고리가 닫히지 않음

형상·공간 후보는 추가로 실제 물체·면, 관찰 단면·기준, 단면에 나타나는 대상, 형상 술어의 주체 및 방향·개방 대상이 원자료에서 하나로 잠겨야 PASS다. 가상 단면·기준선에 실제 면이나 부품이 존재하는 모델만으로 표현할 수 있거나, 형상 술어의 주체가 복수이면 REVIEW 또는 BLOCK이다.

### 5.4 `PRIOR_ART_CONTRIBUTION_GATE`

- `PASS`: 제공된 선행기술 집합과 부모항 전체 조합을 비교했을 때 차이점과 비자명성 논거가 근거와 함께 확인됨
- `REVIEW`: 차이는 있으나 결합동기·예측 가능성 또는 문헌 범위에 판단이 필요함
- `BLOCK`: 부모항 전체 조합에서 부가한정이 만드는 기술기여까지 선행기술에 실질적으로 개시되었거나 통상적 결합·변경임이 확인됨
- `UNVERIFIED`: 선행기술이 없거나 검색 범위가 불충분함

이 게이트의 `PASS`도 등록 가능성을 보증하지 않는다.

### 5.5 `DEPENDENT_DESIGN_GATE`

다음이 모두 충족될 때만 `LOCKED`다.

- 주된 종속항 트리에 포함되는 모든 후보가 `TECHNICAL_SOLUTION_CANDIDATE`
- 주된 종속항 트리에 `TECHNICAL_SOLUTION_CANDIDATE`가 하나 이상 존재함. 하나도 없으면 `UNLOCKED — NO_TECHNICAL_SOLUTION_CANDIDATE`
- 각 포함 후보의 `DEPENDENT_SOURCE_GATE`, `CAUSAL_CONTRIBUTION_GATE`, `CLAIMABILITY_GATE`가 `PASS`
- `DRAWING_ONLY`와 해결되지 않은 `UNVERIFIED` 후보가 주된 트리에서 제외됨
- `FALLBACK_ONLY`는 주된 트리와 분리되고 포함 이유가 명시됨
- 후보별 부모항, 필요한 선행 용어, 권리화 축, 방사형·연쇄형 관계를 포함한 종속항 전략 트리 및 의미 한정 패키지가 확정됨
- 해당하는 모든 형상 후보의 형상·공간 객체 계약이 확정되고, 실제 객체와 관찰 기준이 분리됨
- 루트 LOCK과 USER_LOCK이 보존됨

선행기술 미제공으로 인한 `PRIOR_ART_CONTRIBUTION_GATE: UNVERIFIED`만으로 `UNLOCKED`로 만들지 않는다. 그 대신 모든 후보에 `INVENTIVE_STEP: UNVERIFIED — PRIOR_ART_NOT_PROVIDED`를 표시한다.

## 6. 종속항 세트의 우선순위

주된 세트는 다음 순서로 배치한다.

1. 독립항의 핵심 협동관계를 다른 구체 수단으로 강화하거나 닫는 후보
2. 별도의 기술적 과제를 해결하는 배치·결합·제어·공정 관계 후보
3. 여러 특징이 함께 작동해야 효과가 생기는 결합 후보
4. 원자료가 인과관계를 뒷받침하고, 선행기술이 제공된 경우 그 대비까지 확인된 수치·재료·형상 후보

명확한 예비 보정 가치가 있는 `FALLBACK_ONLY`는 위 주된 세트와 분리된 보조 풀에 둔다.

도면에 눈에 잘 띈다는 이유, 문장으로 쓰기 쉽다는 이유 또는 구성요소 수를 늘릴 수 있다는 이유로 우선순위를 높이지 않는다.

## 7. 식별자·revision·LOCK

- 루트 독립항: 기존 `candidate_id`, `revision: rN`, `design_revision: dN` 유지
- 종속항 세트: 안정적인 `dependent_set_id`
- 종속항 전략 설계: `dependent_design_revision: ddN`
- drafter의 목표 종속항 의미 초안: `dependent_meaning_draft_id`, `dependent_revision_status: PRE_STYLE — NOT_GATE_ELIGIBLE`
- style adjuster가 봉인한 정확한 종속항 세트 문언: `dependent_revision: drN`, `dependent_style_record_id`, `CLAIM_STYLE_GATE`

style adjuster가 봉인한 종속항 문언이 공백·문장부호를 포함해 한 글자라도 바뀌면 같은 `dependent_set_id`의 새 `dependent_revision`을 만들고 dependent style record부터 후속 게이트를 다시 수행한다. 의미 한정 문언이 바뀌면 drafter의 새 PRE_STYLE 초안부터 돌아간다. 후보 집합, 과제–특징–원리–효과, 부모항 전략, 원자료 또는 선행기술 집합이 바뀌면 `dependent_design_revision`도 올리고 이 게이트부터 다시 실행한다. 루트 독립항이나 그 LOCK이 바뀌면 모든 종속항 설계·문언·검수·LOCK은 무효다.

`DRAFT_DEPENDENT_SET_LOCK`은 현재 허용 원자료에 대한 `dependent_style_record_id`, 별도 `claim-success-reviewer`의 `dependent_success_record_id`, CLAIM_STYLE_GATE, TERM_EXPRESSION_GATE, 잠정 기술기여·통사·OA·종속항별 역구성 검증을 봉인한다. `FINAL_DEPENDENT_SET_LOCK`은 같은 후처리·success 기록에 더해 정식 명세서·도면 또는 최초 출원자료에 대한 최종 뒷받침·실시가능성 검증과 종속항별 역구성까지 통과한 경우에만 만든다. PRE_STYLE 의미 초안이나 주 에이전트의 자체 success 판정만으로 어느 LOCK도 만들지 않으며, 어느 LOCK도 선행기술 미제공 상태의 진보성을 PASS로 바꾸지 않는다.

## 8. 필수 출력 형식

- request_mode
- 적용 루트 LOCK과 `candidate_id / revision / design_revision`
- `dependent_set_id`
- `dependent_design_revision`
- USER_LOCK 보존 결과
- 원자료 및 선행기술 집합
- 후보별 필수 인과기록표
- 후보별 형상·공간 객체 계약
- 후보별 네 개의 세부 게이트 판정
- `TECHNICAL_SOLUTION_CANDIDATE` 목록
- 분리된 `FALLBACK_ONLY` 목록과 유지 이유
- 제외한 `DRAWING_ONLY` 목록과 제외 이유
- `UNVERIFIED` 및 필요한 최소 자료
- `RETURN_TO_ARCHITECT` 여부와 이유
- 종속항 전략 트리: 후보 ID / 부모항 / 방사형·연쇄형 관계 / 의미 한정 패키지 / 권리화 축 / 우선순위
- `DEPENDENT_DESIGN_GATE: LOCKED / UNLOCKED`
- `INVENTIVE_STEP: PASS / REVIEW / BLOCK / UNVERIFIED`와 선행기술 범위
- drafter에게 전달할 PRE_STYLE 변경 금지 기술기여 계약
- claim-style-adjuster에게 전달할 표면 문언·형상·공간 객체 계약

이 게이트가 `LOCKED`되기 전에는 종속항 문언을 작성하지 않는다.
